Buddy 5 - Ultrasonic Obstacle Scanning Implementation Specification
===================================================================

This is the current Buddy 5 handoff. It supersedes older Buddy 5 instructions
that mention GP3/GP7, a 10 Hz single-beam sensor, or a Buddy5Ultrasonic API.
Use the Group 19 Design Review, Project Briefing, Project Write-up, and HC-SR04
datasheet as the specification sources.

Ownership
---------

Buddy 5 owns the HC-SR04 ultrasonic sensor and scanning servo. The subsystem
profiles obstacles and publishes a decision to the Vehicle Controller; it does
not drive motors directly.

Frozen design requirements
--------------------------

FR12: Sweep the servo left, center, and right and capture HC-SR04 ECHO pulse
widths through a GPIO ISR to calculate obstacle width and clearance.

FR13: Evaluate left/right clearance and provide the bypass direction to the
Vehicle Controller, which arbitrates navigation and sends motor commands.

NFR8: Complete obstacle detection and the bypass decision in under 3 seconds.

NFR9: Include the 3-point servo sweep at -45, 0, and +45 degrees relative to
the center position.

Project Write-up / Briefing: Use a coarse scan followed by a fine scan when an
obstacle is found; profile location, width, closest point, and side clearance.

Hardware
--------

HC-SR04 TRIG: GP17 (GPIO output)
HC-SR04 ECHO: GP16 (GPIO input and rising/falling edge capture)
Scanning servo signal: GP15 (PWM, 50 Hz)
HC-SR04 supply: 5 V and GND

HC-SR04 ECHO is a 5 V signal. Use a voltage divider or level shifter so GP16
never receives more than 3.3 V. Use a common ground. Power the servo according
to its rating; do not assume the Pico 3.3 V rail can power it.

The sensor requires a trigger pulse of at least 10 us. The datasheet recommends
more than 60 ms between measurement cycles to reduce interference from old
echoes; use at least 66 ms between triggers.

Firmware interface and behavior
-------------------------------

Use the repository's existing API:

    void Buddy5Obstacle_CreateTask(void);

The obstacle task should:

1. Initialize GP17, GP16, GP15, the shared GPIO IRQ route, and an echo-width
   queue.
2. Capture ECHO rising/falling timestamps in the shared GPIO dispatcher ISR.
   The ISR should queue the pulse width only; the task performs calculations.
3. Sweep servo positions 45, 90, and 135 degrees, corresponding to -45, 0, and
   +45 degrees relative to center.
4. On a coarse hit, refine the detected region in 5-degree steps.
5. Calculate distance as:

       distance_cm = echo_width_us * 0.0343 / 2

   Bound valid readings to the sensor's nominal 2-400 cm range. A 30 ms
   no-echo timeout represents maximum range.
6. Populate and publish a complete SYSTEM_EVENT_OBSTACLE:
   detected, scan_complete, center_distance_cm, estimated_width_cm,
   left_clearance_cm, right_clearance_cm, and bypass_direction.
7. Use bypass_direction -1 for left, +1 for right, and 0 when neither side
   meets the clearance threshold. The Vehicle Controller must stop rather than
   select a blocked side when the value is 0.
8. Report initialization, queue, or event-delivery failures explicitly.

The task priority is 3; the Vehicle Controller priority is 4. Use the existing
Robot_GpioIrqRegister() router rather than installing a second GPIO callback.
All motor commands remain owned by Motion Control through the Vehicle
Controller.

Build and verification
----------------------

The repository's configured build needs FREERTOS_KERNEL_PATH set in the
environment when CMake is re-run. In PowerShell:

    $env:FREERTOS_KERNEL_PATH = "C:\Users\<user>\FreeRTOS-Kernel"
    cmake -S . -B build -DROBOT_SIMULATION=ON
    cmake --build build --target robot_car

Also compile with ROBOT_SIMULATION=OFF to check the hardware ISR path. Hardware
verification must confirm pin wiring, ECHO voltage, servo alignment, distance
accuracy, and the under-3-second decision time. A successful firmware build
does not establish those physical results.
